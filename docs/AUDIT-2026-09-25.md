# Ascenda — Audit technique (architecture, fonctionnalités, sécurité, documentation, bonnes pratiques)

Date : 2026-09-25
Périmètre : `ovander/ascenda-backend` (Go 1.25, chi, GORM/PostgreSQL, ~42 k lignes + ~42 k lignes de tests) et `ovander/ascenda-frontend` (Vue 3.5, Vite 8, Pinia, PrimeVue, ~56 k lignes). Branche auditée : `claude/zealous-gates-rduui3` (identique à `main` au moment de l'audit).
Méthode : lecture du code (y compris la librairie `github.com/ovander/backendkit@v1.5.0` qui porte l'auth JWT, le rate limiting et les en-têtes de sécurité), exécution des outils (`go build`, `go vet`, `go test -short`, `gofmt`, `golangci-lint`, `vue-tsc`, `vitest`, `npm audit`), diff routeur ↔ OpenAPI ↔ appels frontend. Chaque constat cité ci-dessous a été vérifié dans le code. Aucun fichier des deux dépôts n'a été modifié en dehors de ce rapport.

---

## 1. Synthèse exécutive

**Verdict global : une base technique solide (moteur de calcul pur et très bien testé, architecture en couches propre, frontend typé sans erreur) mais un produit qui n'est pas prêt pour une exploitation multi-locataire en production.** Les problèmes bloquants sont concentrés dans la couche d'autorisation / isolation des tenants, dans le provisionnement du schéma en production, et dans l'absence totale de CI.

| Axe | Note | Résumé |
|---|---|---|
| Architecture | B | Séparation handler → service → repo → compute respectée, moteur `compute` pur (97 % de couverture), injection explicite, arrêt gracieux exemplaire. Points faibles : handlers qui court-circuitent les services, DTO de validation inutilisés, `ctx` non propagé aux repos. |
| Fonctionnalités | B- | Périmètre très large et presque entièrement implémenté (P&L, cash, bilan, ratios, BEP, cap table, snapshots, IA, analyse de scénario v2). Mais : flux magic-link cassé de bout en bout, redirection post-login jamais honorée, ~40 routes cap table sans UI, suppression de plan qui orphelise toutes les données filles, restauration de snapshot non atomique. |
| Sécurité | **D** | 1 critique (isolation des tenants), 4 élevés (IDOR scénario/plan, dump d'audit, rate limiting inopérant, clone de snapshot vers n'importe quel scénario) côté backend ; 1 élevé (XSS dans les popups d'impression) côté frontend ; 5 vulnérabilités npm en prod (4 high). |
| Documentation | C- | READMEs riches mais factuellement faux sur plusieurs points (fichiers inexistants, ports, rôles, tiers) ; OpenAPI couvre 92 opérations sur 229 ; aucun CHANGELOG / CONTRIBUTING / LICENSE / ADR. |
| Bonnes pratiques | C | Pas de CI ; `HEAD` échoue à `go vet`, à un test unitaire et à `golangci-lint` (71 alertes) ; 255 fichiers Go non formatés ; pas d'ESLint côté frontend ; Dockerfile sur Go 1.22 alors que `go.mod` exige 1.25. |

### Les 8 actions à mener en priorité

1. **Résoudre le tenant depuis la base et refuser les requêtes sans tenant** (`internal/middleware/tenant.go`). Aujourd'hui tout utilisateur dont le JWT ne porte pas `tenant_id` — ce qui est le comportement par défaut de Socrate d'après backendkit — atterrit dans le tenant « Default Workspace » partagé, avec son rôle d'origine (potentiellement `owner`).
2. **Lier chaque `{scenarioId}` (et snapshot) au `{planId}` de la route** dans `PlanAccessMiddleware`, et forcer le rôle `viewer` sur les plans démo.
3. **Rendre le rate limiting effectif** : clé par IP avant authentification, par utilisateur après ; aujourd'hui `/auth/register` et `/auth/magic-link` ne sont pas limités du tout.
4. **Créer une migration SQL de base (`000000_baseline`)** : les tables `tenants`, `users`, `business_plans`, `scenarios`, `products`… n'existent que via GORM `AutoMigrate`, désactivé par défaut en production.
5. **Ajouter des contraintes `ON DELETE CASCADE`** (ou réutiliser `PurgeDemoPlans` dans une transaction) : `DeletePlan` / `DeleteScenario` ne suppriment que la ligne parente.
6. **Échapper le HTML dans les 3 générateurs d'impression** du frontend (`CashView`, `BudgetView`, `FullReportView`) : un nom de produit contenant `<script>` s'exécute dans l'origine de l'application.
7. **Mettre en place une CI minimale** (gofmt, vet, golangci-lint, tests courts + intégration testcontainers ; vue-tsc, vitest, eslint) et remettre `HEAD` au vert.
8. **Corriger le flux magic-link / redirection** (le backend écrase le paramètre OAuth `state` par l'URL de redirection ; le frontend le rejette ensuite comme état invalide) et retirer `@rolldown/binding-linux-arm64-gnu` des `dependencies` (casse `npm ci` sur x64).

## 3. Architecture

### 3.1 Backend

**Ce qui est bien fait**
- Graphe d'imports acyclique : handler → {service, dto, model}, service → {repo, event, compute, model}, repo → model, compute → model. **Aucun fichier de `compute` n'importe GORM.**
- Racine de composition explicite (`cmd/server/bootstrap.go`) en 11 phases ordonnées, bundles `Repo/Service/Handler` injectés par constructeur, aucun état global.
- Moteur `compute` réellement pur (pas de `time.Now`, `rand`, I/O), décimal `shopspring` de bout en bout, 97,2 % de couverture, parallélisme de couche 1 sans partage d'état, rupture de cycle P&L ↔ FiPlan ↔ WCR documentée.
- `event.Emitter` : canal borné (256), 4 workers, recovery par abonné, `Close()` propre. Arrêt gracieux (`main.go`) : drain HTTP → goroutines d'usage IA → émetteur → DB → flush Sentry, avec justification de l'ordre.
- Interfaces repo avec vérifications de conformité à la compilation ; `PlanDeps` comme interface étroite ; interfaces `*Servicer` par handler.
- `/ready` fait un vrai `SELECT 1` ; logs JSON structurés avec request-id ; Sentry en `Repanic: true`.

## 4. Fonctionnalités

### 4.1 Couverture

Le périmètre fonctionnel est presque intégralement implémenté et consommé par le frontend (voir matrice complète en annexe A). Aucun appel frontend ne cible une route inexistante. Points notables :

- **Module cap table au niveau scénario : ~40 routes backend sans UI** (classes d'actions, rounds CRUD, plans d'options, grants, valorisation FastValo, branches, 6 rapports : InGeFiE, waterfall, matrice…). Le frontend n'utilise que le résumé plan-level, les shareholders, la synchro des rounds et le profil pays. Le README frontend revendique pourtant ces fonctionnalités. Décider : livrer l'UI ou marquer l'API expérimentale.
- **Stubs** : `user_service.go:322` (`GetImpact` renvoie `ownedPlans: 0`), placeholder « coming soon » crédits IA dans `TenantSettingsView.vue:117`. Endpoint HTTP de sensibilité non exposé (moteur seul, conforme au plan v2).
- Non consommés par le frontend : `POST /auth/login`, `GET /metadata`, `GET /version`, `PUT /users/me`, `PUT settings/capex-per-hire`.
- **Danger de nommage** : `router.go:508` réutilise `{planId}` pour le plan d'optimisation BEP sous une route qui contient déjà le `{planId}` financier ; chi renvoie la valeur la plus interne et le handler le sait, mais tout futur handler lisant le plan financier à cet endroit obtiendrait le mauvais ID. Renommer `{optPlanId}`.
